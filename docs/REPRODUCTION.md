# MAGE Research Code

[← Back to the project overview](../README.md)

> Run commands from the repository root unless a section specifies another working directory.

## Repository Layout

- `osworld/`: environment and benchmark runner
- `components/Task_generator/`: manual processing and task generation
- `components/Episode_generator/`: GUI trajectory collection
- `components/Model_trainer/`: policy training and analysis
- `components/rap/`: retrieval-augmented planning pipelines for OSWorld and Slack
- `environment/`: GUI client Dockerfiles and compose templates

## Execution Guide

### 1. Prepare Environment

Use separate environments for planning, training, and evaluation. The current
requirements files are not a consistent combined environment:

| Component                     | Dependency file                     | Current constraint                                                                                                |
| ----------------------------- | ----------------------------------- | ----------------------------------------------------------------------------------------------------------------- |
| Planning                      | `components/rap/requirements.txt` | Includes OSWorld planning dependencies;`transformers>=4.51.0`                                                   |
| Training / episode generation | `components/requirements.txt`     | Pins`transformers==4.46.0`                                                                                      |
| Evaluation                    | `osworld/requirements.txt`        | Pins`transformers~=4.35.2`, while the local agent imports `AutoModelForImageTextToText` and loads UI-TARS-1.5 |
| GUI clients                   | `environment/requirements.txt`    | Includes`components/requirements.txt` for shared runtime dependencies                                           |

The evaluation dependency pin needs reconciliation with the local agent before
model execution. Installing all four files sequentially will replace packages
required by other components. Run `python -m pip check` in each prepared
environment; it checks package constraints, not model compatibility.
Python metadata also differs: `osworld/setup.py` specifies 3.10+, while
`osworld/pyproject.toml` specifies 3.12+. Select the environment for the installation
method you use; these files do not establish one tested Python version for all stages.
PDF rendering additionally requires the Poppler tools used by `pdf2image`.

Set API credentials if you run API-backed generation/evaluation:

```bash
export OPENAI_API_KEY="your_openai_api_key_here"
```

Optionally copy the environment template and edit local paths:

```bash
cp .env.example .env.local
# Edit .env.local, then export its values into this shell:
set -a
source .env.local
set +a
```

### 2. Prepare Runtime Paths

The training example in section 5 writes a local config using these variables.
Existing cycle configs have their own path expressions; they do not automatically
use `OUTPUT_ROOT`. Set absolute paths before preparing that local config:

```bash
export DATA_ROOT=/path/to/data_root
export OUTPUT_ROOT=/path/to/output_root
```

Evaluation commands are run from `osworld/` and use the fixed evaluation
examples plus an optional LoRA adapter:

```bash
export TEST_ALL_META_PATH=evaluation_examples/test_all.json
export TEST_CONFIG_BASE_DIR=evaluation_examples
export LORA_PATH="/path/to/extracted/UI-TARS-1.5/<application-directory>"
```

To evaluate with retrieval-augmented instructions generated by
`components/rap/`, point the same variables at the precomputed
`libreoffice_plan` task set:

```bash
export TEST_ALL_META_PATH=../components/rap/OSWorld/Plan/libreoffice_plan/test_all.json
export TEST_CONFIG_BASE_DIR=../components/rap/OSWorld/Plan/libreoffice_plan
export LORA_PATH="/path/to/extracted/UI-TARS-1.5/<application-directory>"
```

Set `LORA_PATH` to the application directory containing the adapter configuration
and weights when evaluating a LoRA-adapted model.

### 3. Run LibreOffice Task Generation

The LibreOffice task-generation workspace is included at
`components/Task_generator/Libreoffice/`. It contains the source manuals, generation
code, candidate tasks, and intermediate JSON plans.

Inputs:

- LibreOffice manuals in `components/Task_generator/Libreoffice/pdf/`
- Program configs in `components/Task_generator/Libreoffice/code/config/`
- `OPENAI_API_KEY` for API-backed task generation

Both scripts select the program from `LIBREOFFICE_TASKGEN_PROGRAM`
(`calc`, `impress`, or `writer`). Example for Writer:

```bash
cd components/Task_generator/Libreoffice/code

export OPENAI_API_KEY="your_openai_api_key_here"
export LIBREOFFICE_TASKGEN_ROOT=..
export LIBREOFFICE_TASKGEN_PROGRAM=writer

python build_manual_pipeline.py
python gpt_infer.py
```

Outputs are written into the corresponding program directory under
`components/Task_generator/Libreoffice/`. `build_manual_pipeline.py` generates the
program-specific `images/`, `section.json`, and filtered section JSON before
`gpt_infer.py` performs image-conditioned generation.

### 4. Run Episode Generation

Episode generation turns task JSON entries into GUI interaction trajectories.
This stage runs a socket server and expects a matching GUI client/container to
connect. It requires `OPENAI_API_KEY`; a LoRA adapter can optionally be
passed through `LORA_PATH`.

Training task JSON inputs:

- `components/Episode_generator/Task/calc_train.json`
- `components/Episode_generator/Task/impress_train.json`
- `components/Episode_generator/Task/writer_train.json`

Choose one server command below per terminal; each runs until stopped.
For these base-model examples, clear an inherited evaluation adapter path first:

```bash
cd components/Episode_generator
unset LORA_PATH

export OPENAI_API_KEY="your_openai_api_key_here"

MOD=train BASE_DIR=./test/calc_train/repro START_TASK_IDX=0 END_TASK_IDX=10 \
  PORT=3333 bash run_calc.sh

MOD=train BASE_DIR=./test/impress_train/repro START_TASK_IDX=0 END_TASK_IDX=10 \
  PORT=6666 bash run_impress.sh

MOD=train BASE_DIR=./test/writer_train/repro START_TASK_IDX=0 END_TASK_IDX=10 \
  PORT=8888 bash run_writer.sh
```

Runtime options:

- `MOD`: `train` or `val`
- `BASE_DIR`: output directory for generated trajectories
- `START_TASK_IDX` / `END_TASK_IDX`: task slice to generate
- `TRAJECTORY_NUM`: trajectories per task
- `MAX_STEP`: maximum interaction steps per episode
- `WITH_STEP`: include step-wise procedure context when set to `1`
- `RAG`: enable retrieval augmentation when set to `1`
- `LORA_PATH`: optional parent directory containing numbered epoch directories
- `LORA_EPOCHS`: epoch directory selected by the wrapper (default: `1`)

Unlike evaluation, episode generation appends the epoch to `LORA_PATH`: with
`LORA_PATH=/path/to/run` and `LORA_EPOCHS=1`, it loads `/path/to/run/1`.
A missing epoch directory is skipped. Do not pass a flat downloaded adapter
directory as though it were an evaluation `LORA_PATH`.

### 4.1. Start Docker GUI Clients

The episode-generation server expects one or more GUI clients to connect over a
socket. The Docker clients live under `environment/` and provide VNC/noVNC
desktops for Calc, Impress, Writer, Slack, GIMP, and VS Code.

Build the images:

```bash
cd environment
cp -n .env.example .env
# Edit .env: set VNC_PW and the agent server address and ports.
docker compose --profile build build
```

Choose a free socket port for each episode-generation server. Start the server
first, then start the matching client container with the same `PORT`. The
wrapper scripts have fallback values; set
`PORT` explicitly. Example for Writer:

```bash
cd components/Episode_generator
unset LORA_PATH
MOD=train BASE_DIR=./test/writer_train/repro START_TASK_IDX=0 END_TASK_IDX=10 \
  PORT=8888 bash run_writer.sh
```

In another shell:

```bash
cd environment
WRITER_SERVER_PORT=8888 docker compose --profile writer up writer_1
```

Domain mapping:

| Domain  | Server Script      | Image                      |
| ------- | ------------------ | -------------------------- |
| Calc    | `run_calc.sh`    | `lam-gui-calc:latest`    |
| Impress | `run_impress.sh` | `lam-gui-impress:latest` |
| Writer  | `run_writer.sh`  | `lam-gui-writer:latest`  |

noVNC is exposed on the mapped `6901` port; for the Writer example above, open
`http://localhost:6087` to inspect the desktop. See
[the environment guide](../environment/README.md) for domain-specific setup paths, Slack settings, and
the socket protocol handled by the client. Compose reads `VNC_PW` from
`environment/.env`; the explicit port override matches the Writer server above.

### 5. Run Training

Download the [training trajectories](https://anonymous-hf.com/a/he3p2p7rtgw3/)
and follow the [extraction and layout notes](ARTIFACTS.md#trajectory-dataset).
The archives contain collected episodes. From the repository root, prepare one
application with [`prepare_train.py`](../components/Model_trainer/prepare_train.py).
For the UI-TARS Writer configuration used below:

```bash
python components/Model_trainer/prepare_train.py /path/to/trajectories/UI-TARS/3_libreoffice_writer --dry-run
python components/Model_trainer/prepare_train.py /path/to/trajectories/UI-TARS/3_libreoffice_writer
```

The script groups episodes by exact JSON `real_input` text (falling back to
`project`), combining all input subfolders without parsing folder names. It
copies the episodes into `3_libreoffice_writer_train/` beside the input folder
and generates task-group `info.json` files. See
[preparation details](ARTIFACTS.md#prepare-training-groups) for the output layout
and interrupted-copy handling.

The loader expects task-group directories under `data_root`. Each group needs
an `info.json` with `sample_number` entries and matching trajectory subdirectories
containing trajectory JSON and image files. Groups with no reward variation are
skipped. Task JSONs alone are not training inputs.

Create a local configuration from the existing Writer cycle config. This example
uses one GPU and overrides the dataset and output paths explicitly. It launches
training on the selected dataset; it does not orchestrate the paper's full
round-based collection and training schedule:

```bash
export DATA_ROOT=/path/to/trajectories/UI-TARS/3_libreoffice_writer_train
export OUTPUT_ROOT=/absolute/path/to/training_output

cd components
python - <<'PYCONFIG'
import json
import os
from pathlib import Path

config = json.loads(Path("Model_trainer/config/train/Cycle_1_writer.json").read_text())
config["launcher"]["include"] = "localhost:0"
config["args"]["data_root"] = os.environ["DATA_ROOT"]
config["args"]["output_dir"] = os.environ["OUTPUT_ROOT"]
Path("Model_trainer/config/train/local_writer.json").write_text(
    json.dumps(config, indent=2) + "\n"
)
PYCONFIG
bash Model_trainer/scripts/train/train_template.sh \
  Model_trainer/config/train/local_writer.json
```

For multiple GPUs, set `launcher.include` in the local config to the intended
GPU IDs, for example `localhost:0,1`. Set `args.data_root` to the complete
prepared dataset path as shown above. Relative argument paths are resolved
against `components/` by `run_grpo_from_config.py`.

#### Training Scope and Reward Definition

For the paper's round-based procedure, collect new episodes with the updated
policy, combine them with episodes available from earlier rounds, and prepare
that round's dataset before the next training run. `prepare_train.py` merges
all episodes below its input directory; it does not select round boundaries.
See Section 3.3.3 and Appendix A.2 of the paper for the backbone-specific
schedule.

The current [reward implementation](../components/Model_trainer/grpo_lib/data.py)
uses a fixed maximum step count of 50 and the minimum successful episode length
recorded by the preparation script. Equation (2) in the manuscript instead
defines the maximum and minimum over episodes of the same task. These definitions
can produce different rewards. The current code has not been reconciled here
with the experiment version; this training example should not be treated as
verified reproduction of the reported results.

### 6. Run Evaluation

Evaluation uses the OSWorld Docker provider by default. Make sure Docker is
installed, the daemon is running, and the host supports the GUI environment
requirements described in `osworld/SETUP_GUIDELINE.md` and
`osworld/desktop_env/providers/docker/DOCKER_GUIDELINE.md`.
The runner creates `osworld/logs/` automatically when needed; generated logs and
results are ignored by git.

There are two evaluation task sets:

- Base OSWorld tasks: `osworld/evaluation_examples/`
- Retrieval-augmented tasks: `components/rap/OSWorld/Plan/libreoffice_plan/`

The retrieval-augmented set contains the same LibreOffice task ids with
manual-derived procedures appended to the instruction field. It currently
contains 47 Calc tasks, 47 Impress tasks, and 23 Writer tasks.

Single-domain evaluation wrappers:

TEST_CONFIG_BASE_DIR=evaluation_examples \
LORA_PATH=/path/to/extracted/UI-TARS-1.5/2_libreoffice_impress \
bash run_impress.sh

CUDA_VISIBLE_DEVICES=0 \
RESULT_DIR=./results/repro/writer \

Direct runner example for Calc (equivalent domain selection):

```bash
cd osworld
CUDA_VISIBLE_DEVICES=0 \
python scripts/python/run_multienv_uitars15_v1.py \
  --result_dir ./results/repro/calc \
  --max_steps 50 \
  --num_envs 3 \

```

Read scores from each wrapper's result root (the reader does not search
recursively through `calc/`, `impress/`, and `writer/`):

```bash
cd osworld
for domain in calc impress writer; do
  python show_result.py \
    --action_space pyautogui \
    --observation_type screenshot \
    --model uitars15-7b \
    --result_dir "./results/repro/$domain" \

```

These commands print each run separately, not a combined overall average.
For retrieval-augmented runs, use `./results/repro_rag/$domain` instead.

does not switch the backbone to EvoCUA.

#### 6.3. Regenerate Retrieval-Augmented Tasks

See [the planning guide](../components/rap/README.md) for OSWorld,
Slack, and retrieval-ablation commands. The precomputed LibreOffice task directory is `components/rap/OSWorld/Plan/libreoffice_plan/`. To regenerate it, run
`components/rap/OSWorld/run_local_model.py` with the desired program, manual JSON,
input task set, and output directory. GPU defaults in `config.py` use device 1
for embeddings and devices 0,1,2,3 for generation; set `RBP_EMBED_DEVICE_NUM`
and `RBP_GENERATION_DEVICE_NUMS` for your hardware and available model memory.

Calc example:

```bash
cd components/rap/OSWorld
RBP_PROGRAM_NAME=libreoffice_calc \
RBP_MANUAL_PATH=../../Task_generator/Libreoffice/calc/section_filtered.json \
RBP_EVALUATION_EXAMPLES_ROOT=../../../osworld/evaluation_examples \
RBP_OUTPUT_ROOT=./outputs/calc_tmp \
RBP_FIRST_IMAGE_ROOT=./first_screen_images \
python run_local_model.py
```

For a local input check without loading models or writing output:

```bash
cd components/rap/OSWorld
RBP_PROGRAM_NAME=libreoffice_calc \
RBP_MANUAL_PATH=../../Task_generator/Libreoffice/calc/section_filtered.json \
RBP_EVALUATION_EXAMPLES_ROOT=../../../osworld/evaluation_examples \
RBP_OUTPUT_ROOT=./outputs/calc_smoke \
python run_local_model.py --dry-run --max_examples 2
```

The dry run reports how many first-screen images match the selected tasks.
It can succeed with `screenshots=0`; that does not validate image-conditioned
generation or GPU/model loading. Set `RBP_FIRST_IMAGE_ROOT` to populated
screenshot inputs to include images in generation.

Program-specific manual inputs:

| Program | `RBP_PROGRAM_NAME`    | `RBP_MANUAL_PATH`                                                |
| ------- | ----------------------- | ------------------------------------------------------------------ |
| Calc    | `libreoffice_calc`    | `../../Task_generator/Libreoffice/calc/section_filtered.json`    |
| Impress | `libreoffice_impress` | `../../Task_generator/Libreoffice/Impress/section_filtered.json` |
| Writer  | `libreoffice_writer`  | `../../Task_generator/Libreoffice/Writer/section_filtered.json`  |

`run_local_model.py` refuses an existing `RBP_OUTPUT_ROOT` unless `--overwrite`
is supplied. Use a separate output directory for regeneration runs. The generator writes
`examples/<program>/*.json` plus filtered
`test_all.json`, `test_small.json`, `test_nogdrive.json`, and
`test_infeasible.json` files. If you regenerate multiple programs into one
shared output directory, merge the `test_*.json` domain entries or write each
program into a temporary directory and combine the `examples/` folders and
metadata afterward.
